Scope: `results/run_24_v9_smoke` (v9_recurrent, rich_3486 and rich_3506, vllm-metal, docker sandbox,
both tasks timed out at 244 to 245 s, 0/2 resolved), the harness `edit_file`, `fix_edit.py`, and the
`code_editor_agent` sub-agent. Every claim below was checked this session against the trace JSON, the
task snapshots in `DataSets/public/data/snapshots/`, or the installed harness code.

Method: a replay script re-applied every `edit_file` call of both traces, in order, to a fresh copy of
the task snapshot with the harness's own matcher (`adk_eval_core.editing.edit.apply_replacement`).
The replay reproduced the trace exactly (3 ok, 6 failed). Each failed call was then also sent through
v9's `fix_edit.run` and v10's.

## Correction to the brief

The brief said 6 of 10 `edit_file` calls failed. The traces hold **9** `edit_file` calls (3 in

## The six failed calls

None failed on whitespace or indentation. In all six, `old_string` was text that was **not in the
file at that moment**. The harness matcher already tries exact, then whitespace-flexible, then regex,
then JSON-unescaped matching (`.venv-harness/lib/python3.13/site-packages/adk_eval_core/editing/edit.py:401-454`),
so a pure whitespace slip would have matched.

## Findings, by severity

**F1 (critical): fix_edit was never called; failed edits were resent instead.** 0 `fix_edit.py`
calls in run_24; 2 of 6 failures are exact resends. The rule sits in the middle of a 63-line prompt
(`AgenticSubmission/v9_recurrent/prompts/system.md:28`) as "do not send it again", next to a section
that tells the agent to hand edits to the sub-agent instead (`system.md:20-22`). The harness error
text itself says "check whitespace, indentation, and context", which points the model at the wrong
cause. v10: the rule is now "your very next call is fix_edit with the same three values; never resend
a failed edit_file", and the Viewer -> Editor section is gone.

**F2 (critical): no instruction that a successful edit changes the file.** 4 of 6 failures quote a
read made before the model's own successful edit, although that edit's result carried the new text in
its `diff`. v9's prompt only says "read the exact lines you will change before every edit"
(`system.md:26`). v10 adds: take the next `old_string` from the returned diff or a fresh read, never
from a read made before that edit. `fix_edit.py` now also says so when it detects it (`stale: true`
when `old_string` is in the baseline file; `already_edited` on a candidate block that differs from the
baseline). Replay with v10: #3 and #4 get "old_string is the text from BEFORE an earlier edit of this
file"; #5 and #6 get "the closest block already holds an earlier edit of yours".

**F3 (high): the code_editor sub-agent cannot do what its prompt says, and costs a quarter of the
budget.** `sub_agents/code_editor.yaml:5-9` lists `read_file, edit_file, write_file, run_command` and
no `skills:`, so `run_skill_script` (and `fix_edit.py`) is not available to it, while its description
says it "runs fix_edit/verify" and its prompt (`prompts/editor.md:11`) tells it to hand off to fix_edit.
It starts with an empty context, so it re-reads a file the root agent had already read; `read_file`
caps at 150 lines, and the prompt does not say so. In rich_3486 it ran from 127.6 s to 195.7 s
(68 s of 240 s) and produced the hallucinated anchor of #1. In rich_3506 it started at 214.5 s and
was killed by the timeout. `prompts/editor.md:14` ends with a stray `  EOF` (heredoc residue). Its reply
format is free prose; ADK wraps non-JSON sub-agent text as `{"raw": ...}`
(`adk_eval_core/utils/utils.py:34,53`) and returns `''` when the last event holds no text
(`google/adk/tools/agent_tool.py:281-282`), which the root agent cannot act on.
v10: the editor has `skills: [skills/semdag]`, no `edit_file`, edits by line range through
`fix_edit.py` (no re-typed anchor), finds lines with `grep -n` on code text, and must end with one
`EDIT_OK ...` or `EDIT_FAILED ...` line. The root prompt makes it a last resort (fix_edit failed twice).

**F4 (high): fix_edit candidates were cut to the length of old_string.** A one-line guess at a
multi-line call returned one line (`fix_edit.py:409-410` in v9), and its reference could not be
replaced validly. v10 grows each candidate until its brackets close (`complete_statement`, tokenizer
based, at most 30 lines). Replay: #1 and #2 now show `rich/traceback.py` lines 452-466, the whole call.

**F5 (medium): fix_edit reindent only moved text right.** `reindent` (`fix_edit.py:129-139` in v9)
shifted new text right when it was shallower, never left, so the 8-extra-spaces text of #2 would have
been refused as a syntax error even with the right block. v10 also shifts left when every line carries
the extra indentation.

**F6 (medium): flow output was never used.** 0 `--flow` calls in run_24, although rich_3506's
target `Segment._split_cells` has a `while` loop carrying `cell_pos` and `pos` (the bug is in that
loop's exit). The prompt made it optional (`system.md:18`). v10: locate prints `flow` for the top two
sites itself (rich_3506 snapshot: `{"site":"Segment._split_cells","loops":[{"at":"130-144","kind":"while","carried":["cell_pos","pos"],"exits":{"return":2}}],...}`).

**F7 (low): wall time per model turn dominates.** In run_24 the gap between root-agent tool calls
was 1.4 to 52.9 s (median about 8 s; the 77 s gap in rich_3486 is the sub-agent call). rich_3486
reached its first edit at 116 s, rich_3506 at 78 s. Not addressed here; it is why the sub-agent's 68 s
mattered.

## What the harness edit tool can and cannot be made to do

`edit_file` is a harness tool (`adk_eval_core/editing/edit.py`), not part of the submission, so its
matching and its error text cannot be changed by a submission. "Forgiving matching" and "show the
failing region" therefore live in `fix_edit.py`, which already had whitespace-normalised matching, a
unique-match check, nearest-block display with references, and a syntax guard; v10 adds statement
growth, left reindent, and stale detection. The prompt is the only way to route a failed `edit_file`
to it.
