# Battle axes: NVIDIA assets to convert into our own tuned, vendor-agnostic tools

Written 2026-11-12. Rule for everything below: **no synthetic code or data ships or is reported.** A tool counts as built only if it has run on the real tasks, in the real harness, and its output is on disk.

## Why convert instead of use

The NVIDIA stack cannot ship (fixed vLLM runtime, offline, YAML + `.py` skills + PEFT only), several pieces need NIMs, Kubernetes or NVIDIA API keys, and the harness already owns the call layer. What transfers is the workflow. Each axe below is the smallest stdlib tool that does that workflow's job against `swegemma`.

## Excluded

- **`data-designer`**: synthetic data generation. Conflicts with the no-synthetic rule.
- **`nemo-relay-plugin-adaptive-tuning`**, **`dynamo-*`**: serving and runtime tuning. The scoring runtime is fixed.
- **`nemotron-policy-generator`**, **`nemo-mbridge-*`**, **`cdf-*`**: content safety, large-scale training infrastructure, video curation. No role here.

## Findings, 2026-11-12 (all VERIFIED against on-disk outputs; commands and dirs in the row above)

- **Axe 4 works from the real traces, nothing had to be re-run.** `traces/trace_*.json` (schema `ATIF-v1.7`) records every tool call as `steps[].tool_calls[{function_name, arguments, extra.elapsed_s}]` with a matching `observation` result, plus per-step metrics. First-edit time is the `elapsed_s` of the first `edit_file` call; `locate` is identified by `run_skill_script` with `skill_name: locate`, whose observation JSON carries the printed candidates.
- **A field-level census first said "no tool events"; that reading was wrong** and is withdrawn. It counted only `extra.event_type` (which is `thinking`/`final` for model steps) and missed the `tool_calls` field entirely. The corrected census is what the reader above uses.
- **The arms really are paired.** 23 tasks appear in both arms once all six run dirs are unioned per arm; no task is unique to either arm. Baseline 4/23 (17.4%), bm25 7/23 (30.4%), `base_only: []`, `test_only: [rich_2725, rich_2943, rich_3468]`. bm25 is also cheaper per task: mean 162.2 s vs 197.3 s, mean 9.39 tool calls vs 11.43, 0 errors vs 1.
- **One baseline pass is an empty patch.** `requests_7427` resolves with a 0-byte patch, so it cannot separate the arms; `paired_report.py` counts it in `resolved_by_empty_patch_in_either`.
- **Localization is not the bottleneck.** In the bm25 arm, `locate`'s top 5 held the gold function in 11 of 16 calls and the function the agent edited in 13 of 16; every requests and httpx verdict is identical across arms, and all three gains are `rich` tasks. 4 of the 20 bm25 tasks had the gold function in `locate`'s top 5, edited it, and still failed: the loss is in the edit and the test loop, not in retrieval.
- **`locate` wastes a candidate slot in nearly every call** (`.adk_exec_<hex>.py`, the harness's own skill wrapper, is a scored candidate). Its `SKIP` set has no dotfile entry. This is a defect in axe 1, visible only through axe 4.
