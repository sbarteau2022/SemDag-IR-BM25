**Status:** design, pre-build. **Target:** `gemma-4-E4B-it` QAT (`w4a16-ct`) SWE
dev agent. **Scored metric:** `swegemma` `resolution_rate` (patch makes the
hidden tests pass). **Hard rules:** single model + LoRA, adapter precision must
match the QAT checkpoint, total submission `< 3 GiB`, 32,768-token context,
offline eval, tight per-task budget (sample: 10 tool calls / 1 min / 50 turns).

> **Doctrine — high quality only, built from scratch, no exceptions.**
> Every training example is *executed/verified*, provenance- and license-tracked,
> deduped, and decontaminated against the 129 eval instances. No scraped or
> unverified SFT. If an example cannot show a receipt (a passing test, a runnable
> check, a deterministic grade), it does not enter the set.

## 1. Why a from-scratch SWE LoRA (not reused / not gold-patch SFT)

- Your Qwen adapters (CyberStrike/math/code) **cannot** attach to Gemma-4 —
  different architecture, no corresponding tensors. Capability transfers only by
  distillation, not weight reuse.
- No code/offensive-cyber LoRAs exist for `gemma-4-E4B` on HF; the two math
  fine-tunes are bnb/merged, not QAT-matched. So we build.
- **Gold patches alone are too shallow.** The gold `patch` is an *answer*, not a
  *process*. We train the **process**: reason-first planning, budgeted tool use,
  verifier-grounded iteration, memory. The gold patch is only the terminal
  receipt that accepts a trajectory.

## 2. Capabilities the LoRA must make native (each → a training objective)

1. **Reason-first, then temp-0 execute.** Two phases per turn: deliberate in the
   `<|channel>thought` block (plan, hypotheses, chosen approach), then emit tool
   calls / edits **deterministically at temp 0**. Planning is where entropy lives;
   action is deterministic. Traces separate PLAN tokens from ACT tokens.
2. **Deep Python (not just diffs).** Repo navigation, import/typing/semantics,
   test design, stdlib fluency, debugging from tracebacks, refactors — the
   substrate that makes patches correct across unfamiliar repos.
3. **Active Inference / Free-Energy minimization in the reasoning.** Each step is
   framed as minimizing expected free energy: hold candidate approaches
   (superposition), score each by `complexity − accuracy + β·cost`, act on the
   minimum, then **update beliefs from the deterministic observation**
   (`repo_eval` verdict + test result). This reuses the harness FEP/superposition
   logic as the *reasoning schema*, not just runtime.
4. **Multi-turn tool allocation.** Budget-aware tool planning: localize once
   (`repo_eval` baseline), targeted reads only where the plan needs them, edit,
   verify. Minimize calls under the hard budget; never explore blindly.
5. **No blind retry — dynamic iteration.** On a failed quality gate (red
   `repo_eval` verdict, failing test), **re-reason and change approach** — a
   different hypothesis or edit site — never repeat the failed action. "Same gap
   twice → step back." Trained from failed→switch→pass episodes.
6. **Self-improvement loops.** Within-task (edit→verify→re-plan until clean) and
   the discipline of converting a failure into a changed plan, not a retry.
7. **Native `memory.md` (no reliance on compaction).** The agent maintains an
   explicit working `memory.md` — repo facts, decisions, approaches tried,
   dead-ends, the current plan — written/read via `write_file`/`read_file` as a
   first-class action. Under a 32k window, memory must be an *artifact the model
   curates*, not context it hopes survives compaction. Trained so updating and
   consulting memory is reflexive, and reading it prevents repeating a dead-end.

## 3. Datasets (all built from scratch, verified, decontaminated)

Each family is generated by **us**, filtered by the **deterministic `repo_eval`
automaton + the repo's own tests** as the acceptance oracle (ground-truth,
non-driftable). Trajectories are recorded in the Gemma-4 channel format
(thinking → tool calls → tool responses) so the LoRA learns the real protocol.

| ID | Family | What it teaches | Acceptance gate |
| :-- | :-- | :-- | :-- |
| **D1** | **SWE reason→act→verify trajectories** (core) | Full process: plan, localize, edit, verify, iterate to a passing patch | Repo's own tests pass; `repo_eval clean`; patch applies |
| **D2** | **Deep-Python competency** | typing, stdlib, data structures, algorithms, debugging-from-traceback | Each exercise has a runnable test oracle that passes |
| **D3** | **FEP / Active-Inference reasoning** | enumerate candidate approaches → score (accuracy vs cost) → select min-F → update on observation | Chosen path verified; schema-validated; coherence-checked |
| **D4** | **Dynamic-iteration / failure recovery** | first approach fails the verifier → re-reason → switch approach → pass (never repeat) | Episode contains a real red verdict then a distinct approach that goes green |
| **D5** | **Tool allocation under budget** | minimal-call tool plans (localize once, targeted reads, verify) | Task solved within the budget ceiling; call-count labeled |
| **D6** | **`memory.md` maintenance** | write/update memory after each step; read it to avoid re-derivation and repeated failures | Paired trace shows a memory read preventing a repeat of a logged dead-end |

**Sources (license-clean, permissive only):**
- Real Python repos with permissive licenses + their existing test suites.
- **Self-generated tasks**: take a permissive repo at a commit, introduce a
  localized defect, require the fix that restores its tests (process data at
  scale, fully verified, never touching the eval set).
- Teacher-generated trajectories (strong model) **accepted only on a passing
  verifier** — the teacher's *reasoning* is kept; its *correctness* is earned by
  the oracle, not assumed.

**Quality gates — enforced, no exceptions:**
- **Executed/verified only.** No example without a passing receipt.
- **Decontamination (hard):** exclude all 129 eval `instance_id`s and their
  `repo@base_commit` from every family; near-dup check against eval problem text.
- **Dedup:** content hash + near-duplicate filter across families.
- **Schema + length:** valid Gemma-4 turn structure; ≤ 32k tokens.
- **Balance:** cap per-repo and per-pattern share to prevent memorization.
- **Provenance + license** recorded per example; negatives logged, not hidden.
- **Assistant-only loss masking**; thinking, tool-call, and `memory.md`-update
  tokens are all learning targets.

## 4. Trace-generation pipeline (offline-friendly)

```
permissive repo @commit
  └─ (self-defect OR real issue)  →  teacher: reason-first trajectory
        └─ deterministic gate: repo_eval (parity+syntax) + repo's own tests
              ├─ PASS  → keep full trajectory (plan+acts+verdicts+patch+receipt)
              │           └─ if it contains a failed→switch→pass arc → also tag D4
              └─ FAIL  → discard the terminal, but mine any verified sub-steps
```
- The **same `repo_eval` automaton** used at inference is the data filter → train
  and eval share one ground truth.
- Reason/act separation is enforced by the channel format (thinking vs tool
  calls). Memory updates are emitted as explicit `write_file memory.md` actions.

## 5. LoRA configuration

- **Base for training:** `google/gemma-4-E4B-it-qat-q4_0-unquantized` (the QAT
  half-precision source), so the trained LoRA serves on the `w4a16-ct`
  checkpoint at **matching QAT precision** (competition rule).
- **Targets:** attention `q/k/v/o` + MLP `gate/up/down` across the 42 layers
  (both sliding and full-attention layers). Exclude tied embeddings / `lm_head`.
- **Rank/alpha:** start r=16–32, α=2×r, dropout 0.05 (sweep after baseline).
- **Template:** Gemma-4 chat template, `enable_thinking=true`, assistant-only
  loss masking (targets include thought, tool calls, memory updates).
- **Budget fit:** keep the final adapter well inside the `< 3 GiB` submission cap
  (r≤32 is tiny); ships as `adapters/main_lora`. Optional second `tool_lora` for
  tool-format discipline only if ablation shows it helps.
- **Context:** train/eval at the 32,768 ceiling.
- **Platform:** train on Kaggle GPU; confirm parity on the 4×L4 CUDA serving path.

## 5b. Training method — SFT seed → RL with verifiable rewards (NeMo stack)

SFT on verified trajectories (§4) is the **seed/cold-start**, not the finish.
The real lever is **RL where the reward is execution-verified** — the current
SOTA for SWE agents and almost certainly what the un-RL'd 31B leaderboard entry
lacks.

- **Reward = `repo_eval`/test verdict.** `repo_eval clean` + repo's own tests
  pass → +reward; red/abstain-wrongly → 0/neg. The deterministic verifier is the
  verifiable reward signal (no learned reward model, no drift).
- **NeMo Gym** supplies the RL environment + rollout collection at scale; **NeMo
  RL** post-trains/aligns the E4B on those rollouts; **AutoModel** does the
  day-zero HF PEFT; **Megatron Bridge** scales it. Skills for all four are
  installed locally.
- **Data tooling:** **Data Designer** (D2/D3 synthetic-from-scratch),
  **Curator** (dedup + decontam quality gates), **User Sim** (D1/D5 multi-turn
  trajectories). **Evaluator / Eval Author** for held-out + behavioral evals.
- **Dev loop:** **Relay + Compass** (= NemoClaw Agent Optimization) trace the
  agent over the 129, mine failures, validate changes pre-ship.
- **Reward shaping bakes in the policy we want:** reward the abstain/no-op when
  nothing verifies; penalize blind-retry (repeating a failed action); reward
  minimal-diff that stays green; reward staying within tool/time budget.
- OFFLINE BOUNDARY: all of this is train-time on Kaggle/our box. The shipped
  artifact is still ADK YAML + E4B LoRA under fixed vLLM; none of the NeMo
  runtime ships.

## 5c. Reasoning schema — harvested from NVIDIA's vuln-analysis blueprint

NVIDIA's own reference design validates the deterministic-first thesis. Bake its
discipline into the D3/D4 reasoning traces and the submit gate:

- **Deterministic pre-triage → early exit; LLM only for ambiguous cases.**
  `repo_eval` localization/syntax/parity runs first; LLM edit-reasoning fires
  only where localization is genuinely ambiguous.
- **Precedence-ordered decision flowchart + recorded decision trace** at the
  submit/abstain gate — the trace is a training target (teaches the reasoning).
- **Patch-confidence verdict taxonomy** driving the action:
  `no-change-needed` / `cannot-localize` / `localized-uncertain` /
  `verified-green` → abstain vs minimal-diff vs submit.
- **Repo filesystem = ground truth** (not a cached SBOM/summary); re-verify after
  every edit.

## 6. Evaluation & acceptance (measure, don't assert)

1. **Baseline first** (commandment: compute the oracle before improving): run
   `swegemma eval` with the current submission, no LoRA → `resolution_rate`.
2. Train → evaluate on a **held-out slice that is NOT the 129** → report lift.
3. **Behavioral assertions** (beyond resolution_rate):
   - reason-before-act present every turn; action phase is temp-0 deterministic;
   - **approach-switch rate on failures ≈ 1.0** (no blind retries);
   - `memory.md` is written and later read within tasks;
   - tool-calls-per-task within budget;
   - verifier-clean before every `submit_patch`.
4. Negative results recorded with the same rigor as positives.

---

## 7. Integrity (the no-exceptions clause, restated as law)

- The 129 eval instances and their repos are **excluded from all training data**,
  verified by `instance_id` and `repo@commit` filters + near-dup text check.
- No example enters the set without an executed receipt.
- Every example carries provenance + license; the dataset manifest is written
  before training and is part of the record.
- The deterministic `repo_eval` verdict is the single source of truth for
  acceptance — training and inference cannot drift apart.
